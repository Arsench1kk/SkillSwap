# Runbook гейта M1: проведение заместителем

Документ описывает, как заместитель проводит гейт выпуска, если основной
владелец гейта недоступен. Это порядок действий, а не новое продуктовое
требование. Права владельцев файлов из [PLAN.md](PLAN.md) не меняются.

## Когда заместитель берёт гейт

- Основной владелец гейта не отвечает в рабочем канале команды в течение
  согласованного окна гейта или заранее сообщил, что будет недоступен.
- Заместитель пишет в канал команды: «Гейт M1 провожу я, кандидат M1-rc1,
  SHA `<полный SHA>`». С этого момента решения по гейту принимает он.
- Заместитель не проверяет свой собственный PR как ревьюер (DoD v2: ревьюер
  не автор). Если кандидат содержит его изменения, их смотрит второй участник.

## 1. Зафиксировать сборку M1-rc1

1. Получить актуальный `main` без перезаписи локальной работы:
   `git status` должен быть чистым, затем `git fetch origin` и
   `git switch --detach origin/main`.
2. Записать полный SHA: `git rev-parse HEAD`. Кандидат M1-rc1 это именно этот
   SHA. Все доказательства ниже ссылаются на него.
3. Если команда использует тег, его ставит владелец выпуска по своему
   процессу (`git tag -a M1-rc1 <SHA>`). Заместитель не переставляет и не
   удаляет существующие теги. Если тег уже есть, сверить, что он указывает на
   записанный SHA.
4. После фиксации кандидат не меняется. Любая правка означает новый кандидат
   (M1-rc2) и повтор всех шагов.

## 2. Автоматические проверки

Выполнять из `apps/web` на зафиксированном SHA. Тестовая база поднимается из
`docker-compose.yml` в корне репозитория, адрес по умолчанию задан в
`apps/web/testing/database-target.ts` (`skillswap_test` на порту 5433).

```
docker compose up -d db
npm ci
npm run db:test:prepare
npm run format:check
npm run lint
npm run typecheck
npm test
npm run test:db
npm run e2e
```

- `npm run test:db` обязателен: без базы `npm test` пропускает PostgreSQL
  наборы, а `test:db` превращает отсутствие базы в ошибку.
- Сравнить результат с CI для того же SHA (job `test-and-build` в
  `.github/workflows/ci.yml`). Расхождение между локальным прогоном и CI
  разбирается до решения, а не повтором до зелёного.
- Для каждой команды записать: команда, SHA, результат, число тестов,
  пропуски и их причина.

## 4. Решение go / no-go

**Go**, если одновременно:

- все команды раздела 2 прошли на зафиксированном SHA, CI для этого SHA зелёный;
- TC-01..TC-06 имеют результат pass;
- нет открытых дефектов P1 по кандидату.

**No-go**, если любое из условий не выполнено. Пропущенная проверка не равна
пройденной: если `test:db` или e2e не удалось запустить, решение no-go или
явное письменное принятие риска основным владельцем гейта.

Решение записывается одной записью: кандидат, SHA, go или no-go, причина,
список приложенных доказательств, кто проводил, дата и время (Алматы).

## 5. Откат на предыдущую сборку

Если после go обнаружен блокирующий дефект:

1. Определить предыдущую принятую сборку (последнее решение go и её SHA).
2. Развернуть этот SHA тем же способом, которым разворачивается выпуск. Новые
   коммиты в `main` для отката не создаются; `main` не переписывается
   (`reset`, `force push` запрещены).
3. Если в кандидате были миграции базы, откат кода не откатывает схему. Перед
   откатом сверить с D1 (Арсен), совместима ли предыдущая сборка с текущей
   схемой. Миграции вручную не откатывать.
4. Повторить после отката раздел 2 и TC-01 на предыдущем SHA.
5. Исправление дефекта идёт обычным PR и новым кандидатом.

## 6. Кого уведомить

- Канал команды: решение go / no-go или факт отката, SHA, ссылка на запись.
- Основного владельца гейта: полный итог, как только он снова доступен.
- D6 (Андрей): результаты CI, e2e и релизного чек-листа.
- D1 (Арсен): при откате или любом вопросе о схеме и миграциях.
- Владельца модуля с дефектом (по таблице владельцев в PLAN.md): описание
  дефекта и шаги воспроизведения без приватных данных.
