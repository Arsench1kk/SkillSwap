# Передачи между участниками и ИИ-агентами

Правило установлено Арсеном 4 ноября 2026 **для всех D1–D6 и любых их агентов**.
Полезный коллегам результат должен сопровождаться доступной им записью; Draft
PR тоже подходит для передачи контракта, но не становится от этого объединённым
или окончательным. Это механизм координации, а не новая продуктовая спецификация.

Перед началом задачи открыть **все шесть журналов**, отфильтровать записи по своему
направлению и читать полные детали у автора. Это позволяет Руслану учитывать
профили Амира, Нурлану — подтверждение пары Руслана, всем — контракты Арсена и
изменения инфраструктуры/строк Андрея, не ожидая специального сообщения в чате.
В каждом персональном задании есть постоянная ссылка на этот индекс.

Автор меняет свой файл, а не пять чужих журналов. Общий индекс не требуется
переписывать после каждого PR. Содержимое персональных задач не дублирует полный
контракт: подробности и версия находятся у автора. Для использования чужого кода
нельзя полагаться только на короткую заметку в задании.

## Когда нужна передача

Перед завершением каждой задачи проверить влияние на другие направления:

- API/TS/Zod-контракт, серверный helper, ошибки, транзакции или права;
- схема, миграция, backfill, совместимость данных;
- строки, tokens/primitives, навигация или точка интеграции UI;
- env/config, зависимости, CI, fixtures, scheduler или способы запуска тестов;
- найденный общий дефект, ограничение, смена владельца либо зависимость/блокер.

Если влияние есть — добавить или обновить запись своего журнала, перечислить
адресатов и сослаться на её ID в PR и итоговом отчёте. Если его нет — достаточно
краткого «межкомандное влияние: нет» в описании PR. Не создавать фиктивные записи
для внутренних правок, которые ничего не меняют для соседних модулей.
Напоминание также включено в общий
[шаблон PR](../../.github/pull_request_template.md).

При новом commit, меняющем обещанный контракт, обновить head SHA, описание
совместимости и действие получателя. После Ready/merge/close/replacement обновить
статус; при замене указать преемника. Не оставлять закрытый PR как актуальную
зависимость. История изменений остаётся в Git.

## Публикация и доступность

Документацию передачи доставлять в `main` отдельно от feature-кода: небольшим
docs PR либо уже разрешённой публикацией только документации. Не добавлять
приложение, секреты или снимки экрана в такой commit. Не обходить branch protection
и требования проверки. Документный PR, ожидающий объединения, ещё не прочтут
агенты, открывающие только `main`: в отчёте явно отметить это и дать ссылку.

В этой публикации переданы записи о PR №1–4. **Сам код этих PR в `main` не
добавляется.** После получения актуального репозитория новые инструкции будут
доступны агентам; уже работающую сессию нужно явно попросить перечитать их.
Это не push-уведомления и не гарантия, что агент без обновления файлов узнает новость.

## Что обязан сделать получатель

1. Сверить свой D-код, адресатов, дату записи, GitHub-статус и полный head SHA.
   Прочитать diff/код соответствующей версии, включая зависимые PR.
2. Различать Draft, Ready и merged. Запись — снимок наблюдения; при изменившемся
   SHA/status обновить понимание по реальному PR, не считать таблицу live API.
3. Определить, требуется ли контракт его текущей задаче. Не реализовывать заново
   уже подготовленный helper и не предполагать наличие Draft-кода в `main`.
4. Для чтения использовать PR или безопасное получение refs и `git show` точного
   SHA. Не выполнять reset/force push и не перезаписывать локальные изменения.
   Для зависимой реализации согласовать base/порядок объединения; не cherry-pick
   чужие shared helpers в несколько конкурирующих копий без координации.
5. Если версия недоступна или решение ещё открыто, обозначить конкретный блокер
   и продолжить независимые части. Это не останавливает весь пакет разработчика.
6. При фактическом использовании либо обнаруженном конфликте оставить в **своём**
   журнале отметку: ID чужой передачи, проверенный SHA, reviewed/adopted/blocked,
   свой integration PR или точная причина. Чтение не означает реализацию;
   отправитель не может принять передачу за получателя. Для каждой просто
   прочитанной справочной записи отдельная отметка не требуется.

Детали передачи не отменяют AGENTS, права владельцев и открытые решения R01–R11.
Продуктовые поля/события/тексты всё равно сначала утверждаются в UX/словаре.

## Шаблон новой записи автора

Скопировать в свой журнал, заполнить реальные данные и убрать placeholders:

```markdown
<a id="d2-h001"></a>

## D2-H001 — краткое название

- Автор: D2 / Руслан. Адресаты: D3, D4.
- Проверено: дата. Статус: draft / ready / merged / closed / superseded.
- PR: ссылка. Ветка: имя. Полный head SHA: значение.
- Base и зависимости: конкретные PR/commits либо «нет».
- Контракт: пути от корня репозитория и точные symbols/API.
- Действие получателя: что читать, переиспользовать или согласовать.
- Совместимость/ограничения: что не подключено, что ещё не утверждено.
- Проверки: команды/результат, пропуски, окружение без секретов.
```

Пример отметки получателя в его собственном журнале:

```markdown
## Прочитанные и применённые передачи

- D1-H001 @ полный SHA — reviewed; используется в моём PR по ссылке.
  Либо blocked: конкретная незакрытая зависимость. Дата проверки.
```
