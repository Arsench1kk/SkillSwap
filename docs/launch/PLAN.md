# План полноценного запуска: шесть разработчиков

Основание: [аудит кода и проверок](AUDIT_2026-11-04.md), 4 ноября 2026.
Цель: рабочие аккаунты, реальные профили и поиск, ручной подбор, встречи, отзывы,
обработка жалоб и проверяемая готовность production. Полный объём с профилями и
поиском выбран пользователем. Новые продуктовые правила ещё не утверждены.

Это план работ, а не разрешение выдумывать поля/экраны/события. Сначала закрыть
зависимые [решения R01–R11](DECISIONS.md). Указанные ниже новые каталоги —
предлагаемые границы кода; они ещё не созданы. Существующие URL сохранять до
явного решения о переходе. Реализовывать по одному экрану/concern на PR.

оценивает PR каждого пакета и перераспределяет только **целые модули** с владельцем.

## Почему сначала нужен общий этап

Кабинет сейчас находится в `prototype-app.tsx` (1969 строк) и одном CSS-модуле
(3607 строк). Отдельные ветки не устранят конфликты, если шесть человек одновременно
переписывают эти файлы. Также нельзя независимо генерировать шесть наборов миграций
с одним Drizzle journal или одновременно менять один каталог строк.

### G0 — общая исходная версия

1. Сохранить текущую работу; она уже находится в локальном `5e661d5` поверх GitHub
   `main`. Этот коммит **ещё не опубликован**. Подготовить и проверить PR общей
   исходной версии; не заставлять команду стартовать от локального SHA, которого
   нет на GitHub. Настоящее объединение/публикация не выполнялись этим планом.
2. D6 делает отдельный PR нормализации форматирования 26 обнаруженных файлов.
   Сделать это **до** ответвления модулей; не смешивать форматирование с фичами.
   Проверить diff и не менять смысл SQL/миграций.
3. D1 выделяет из монолита оболочку и модули по владению ниже, без смены поведения,
   копирования demo в production или нового дизайна. D6 проверяет регрессии.
4. Только после объединения G0 создать шесть веток из одной актуальной `main`:
   `codex/arsen-platform`, `codex/ruslan-learner`, `codex/amir-mentor-profiles`, `codex/nurlan-sessions`,
   `codex/togzhan-operations`, `codex/andrey-release`. Для нескольких PR одного пакета добавлять
   суффикс concern; не держать всю работу в одном огромном PR.

Это условие общего старта относится к разделяемому кабинету и его выделению.
Независимые серверные исправления/контракты могут поставляться отдельными PR до
завершения G0. Зависимость от чужого кода указывать явно через
[протокол передач](HANDOFFS.md); незавершённый пакет коллеги целиком не блокирует
остальные независимые задачи.

### G1 — спецификации и контракты

Решения R01–R11 могут приниматься по группам: auth и исправление явных ошибок не
должны ждать весь профильный документ. Но dependent surfaces нельзя реализовывать
по догадкам. D6 фиксирует решения в UX/словаре, D1 публикует версионированные
TypeScript/Zod контракты и согласованную модель БД. Ранние общие PR объединяются
до потребителей. Полей и экранных ID в этом плане намеренно не придумано.

Пока G0/G1 готовятся, все работают без конкуренции: D2 составляет L1–L3/state
matrix; D3 готовит вопросы/варианты profile/privacy; D4 — lifecycle-инварианты и
регрессии A04/A05; D5 — сценарий P10, access matrix и ручной подбор; D6 — CI и
безопасную тестовую БД; D1 — извлечение модулей и auth-контракты. Это полезная
подготовка, но не шесть независимых реализаций одного и того же экрана.

## Как вносить изменения в общие файлы

Для каждого направления действует [HANDOFFS.md](HANDOFFS.md): перед работой читать
адресованные ему записи, а при влиянии на коллег обновлять свой авторский журнал.
Владение координационными файлами `docs/launch/handoffs/Dn_NAME.md` закреплено за
соответствующим D1–D6; это исключение из общего редакторского владения D6 только
для передач и собственных отметок использования. Оно не меняет права на код/UX.

- Нужна миграция: автор фичи передаёт D1 обоснование, согласованные поля,
  ограничения, backfill и ожидания тестов. **Только D1** меняет schema, генерирует
  migration и journal из актуальной `main`. Проверяет чистую БД и upgrade старой.
  Ветке фичи сначала получить этот PR. Не исправлять номера миграций вручную.
- Нужны строки: автор передаёт D6 ключи и ссылку на утверждённый текст.
  D6 заранее добавляет ключи в `messages/en.ts` и каталоги; фича начинает с этого
  коммита. Не переносить строки inline и не обходить типизацию временными `any`.
- Нужна общая зависимость/скрипт: D6 отдельным PR меняет package/lockfile,
  `.env.example`, тестовую конфигурацию. Указывает версию, лицензию и причину.
- Общая настройка происхождения событий не должна зависеть от mentor-фичи:
  в G0 D1 переносит `currentDataOrigin` из `mentor-brief-page.ts` в общий
  server context, обновляет потребителей и согласует одинаковое поведение
  конфигурации. Сейчас часть путей делает fallback в rehearsal, часть — бросает
  ошибку; дальнейшую production-политику явно зафиксировать в R10.
- Нужен вызов чужого модуля: согласовать вход/выход через контракт, не дублировать
  его SQL/валидацию. Исправление чужой логики делает её владелец.
- Нужна интеграция экрана в оболочку: автор экспортирует готовый компонент по
  согласованному контракту; D1 добавляет его в навигацию отдельным небольшим PR.
  Владельцы фич не переписывают `prototype-app.tsx` параллельно.

## Границы взаимодействия модулей

Названия методов ниже — темы контрактов, а не уже существующие API.

| Поставщик → потребитель | Что зафиксировать до реализации                                                                                                              |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| D1 → D2–D5              | Получение auth/participant контекста по роли, guard оператора, ошибки/статусы, transaction type, безопасный event/token контекст             |
| D3 → D2                 | Утверждённый публичный DTO профиля и predicate «можно показывать»; скрытые/неверифицированные/модерируемые данные не обходятся прямым SQL D2 |
| D2 → D3                 | Поиск возвращает только публичный DTO; выбранный наставник влияет на заявку строго по R02, оператор сохраняет окончательное решение          |
| D4 → D2                 | Создание/получение одной встречи в **переданной транзакции** подтверждения; не отдельный HTTP-запрос после commit                            |
| D3 → D5                 | Команды verification/visibility/moderation: D5 проверяет операторский доступ и вызывает сервис D3, не пишет его таблицы обходным путём       |
| D2/D3 → D5              | Команды eligibility/brief/match из своих модулей с проверкой состояния и audit; D5 оркестрирует утверждённый ручной процесс                  |
| D4 → D5                 | Команды Meet/completion/no-show/cancel и выдача session/rating links, проверки и события внутри D4                                           |
| D4/D5 → D6              | Entry points фоновых задач, требования к cadence/правам и безопасный результат выполнения; D6 подключает scheduler                           |
| D6 → все                | i18n для server/client, ключи, UI tokens/primitives, локальная тестовая БД и fixtures, CI checks                                             |

Фича сама валидирует Zod, применяет права, выполняет изменения и событие в одной
транзакции. Общий `recordEvent` не принимает идентичность из клиента. Не вводить
новые event names до R10. Правила чтения приватного контакта действуют и в SQL,
и в сериализованном ответе, а не только при скрытии элемента интерфейса.

## Порядок поставки

1. **G0:** опубликованная общая база, форматирование, выделение модулей.
2. **G1:** согласованные спецификации, access matrix, ключи, контракты и
   необходимые базовые миграции. Доступы/исправления готовятся параллельно.
3. **Первая вертикаль:** D1 auth → D2 заявка → D5 ручной выбор/приглашение →
   D3 предложение времени → D2 подтверждение + сервис D4 → D4 встреча/отзыв.
   Это порядок зависимости, а не требование ждать окончания всего пакета соседа.
4. **Полнота:** D3 профиль/публикация → D2 поиск/предпочтение; D5 модерация,
   повторный подбор и жалобы; D6 локализация/доступность/эксплуатация.
5. **Интеграционный релиз:** все фичи на staging с отдельной БД, полный прогон,
   исправления владельцами, проба с пользователями, затем решение о запуске.

Ветки регулярно обновляются из `main`; PR небольшие и объединяются по
зависимостям. Не делать force push в общую ветку, не заменять чужой файл своей
версией ради удаления конфликта. Единственный владелец общих файлов уменьшает
конфликты, но не устраняет необходимость интеграции и обсуждения контрактов.

## Проверка результата каждого PR

- Ссылка на утверждённый screen ID/concern и перечень состояний из UX.
- Логика, валидация, права и события проверены тестами автора; отрицательные
  случаи доступа и повторные/одновременные действия покрыты там, где применимо.
- `format:check`, lint, typecheck, unit/integration и затронутый Playwright
  проходят на отдельной тестовой БД; smoke 360 px и клавиатура.
- Новые UI проверены Impeccable critique/detector; tokens и строки из каталога.
- Legacy private links работают согласно согласованной совместимости.
- Указаны новые зависимости либо «нет», миграции, пропуски и незакрытые решения.
- Автор соседнего модуля просматривает изменение контракта. D6 не принимает
  фичу с production-stub или toast вместо настоящей записи.

## Когда можно считать продукт готовым к запуску

1. Два реальных тестовых аккаунта обеих ролей проходят регистрацию/почту/вход,
   восстановление пароля и переключение роли; чужие данные недоступны.
2. Наставник создаёт профиль, оператор проверяет навык, видимость реально
   соблюдается в поиске, деталях и прямом API. Скрытие и модерация проверены.
3. Ученик находит наставника, отправляет заявку с сохранением текста при ошибке;
   оператор вручную принимает решение, наставник отвечает, ученик подтверждает.
4. Встреча создаётся один раз, ссылка ведёт к нужной встрече при нескольких
   встречах пользователя, Meet доступен по правилам взаимного подтверждения.
5. Отмена/withdraw/decline/no-reply/expiry не оставляют противоречивых состояний;
   completion/no-show корректно фиксируются, L5 открывается в допустимый момент.
6. Частичный отзыв сохраняется, ответы не перезаписываются; expiry-job не теряет
   заполненное и повторный запуск безопасен. События без контактов и имён.
7. Жалобу получает уполномоченный оператор; согласованы ответственный и срок;
   согласие/privacy/хранение/отзыв утверждены, а не оставлены TODO.
8. Выбранные в R09 языки проверены на всех production-поверхностях; 360 px,
   клавиатура, focus, контраст и ошибочные/пустые/загрузочные состояния проверены.
9. Свежая установка, upgrade-миграция, production build, CI и полный E2E проходят;
   отдельные staging/production окружения, проверены почта, backup/restore,
   секреты, запуск jobs, rollback и эксплуатационная инструкция.
10. Проведена проверка из UX §11 с реальными студентами: 5 учеников и 5 наставников,
    записаны наблюдения; известные P1 закрыты, остаточные P2 явно приняты командой.

Завершение шести пакетов даёт release candidate. Само по себе количество
закрытых задач или зелёных тестов не заменяет продуктовые решения и пробный запуск.
