## D2-H001 — действия ученика под блокировками и чистые правила заявки

- Автор: D2 / Руслан. Адресаты: D1, D3, D4, D6.
- Проверено: 7 ноября 2026. Статус: **локальная ветка, не закоммичена, PR нет**.
  Полный head SHA появится после коммита; до этого получателям нечего читать в
  GitHub, и запись не должна использоваться как зависимость.
- Ветка: `codex/ruslan-learner-hardening` (от `main` `47cd6cf`).
- Base и зависимости: только `main`. Код D1 из Draft PR №1–№6 не использован.
- Контракт (пути от корня репозитория):
  - `apps/web/src/services/learner/request-actions.ts` — `confirmLearnerMatch`,
    `declineLearnerMatch`, `cancelLearnerRequest`, `updateLearnerRequest`;
    результат `{ ok: true } | { ok: false, error: "state_changed" | "invalid_update" }`.
    Принимают `NodePgDatabase` или транзакцию, поэтому D4 сможет вызвать их внутри
    своей транзакции.
  - `apps/web/src/domain/learner-request-submission-rules.ts` — чистые правила
    заявки (`learnerRequestInputSchema`, `contactIsValid`, `deadlineIsEligible`,
    даты). Без импорта БД, можно использовать в браузере.
  - `apps/web/src/domain/learner-status.ts` — `deriveLearnerStatusState`.
- Порядок блокировок для действий над предложением времени:
  `mentor_briefs` → `learner_requests` → `matches`. Он совпадает с существующими
  маршрутами наставника (сначала brief, потом update match). **D3/D4/D5:** если
  берёте эти строки в одной транзакции, сохраняйте порядок, иначе возможен deadlock.
- Действие получателей:
  - D3: отказ ученика теперь не перезаписывает `withdrawn` на `declined`
    (раньше при гонке так и происходило). Ваш withdraw в `app/api/brief/action`
    по-прежнему обновляет `matches` без предиката по статусу; рекомендую условное
    обновление.
  - D4: при подтверждении сессию нужно создавать в той же транзакции; точка
    расширения — конец `confirmLearnerMatch` после обновления `matches`. Пока этот
    контракт D4 не готов, сессия не создаётся (A03 не закрыт).
  - D6: нужны ключи строк (см. ниже) и подключение `e2e/learner/**` в CI.
  - D1: A06 по-прежнему ждёт решения R08 и модели хранения контакта.
- Нужные строки (в форме L1 временно используются ближайшие существующие):
  отдельный текст для неверного формата контакта (сейчас `requestContactRequired`),
  для окна времени в прошлом и для превышения лимита попыток (сейчас
  `requestFixErrors` / `requestNetworkError`).
- Совместимость: HTTP-контракт `/api/request/status` не менялся (те же коды 400/409/410/429/503).
  Старые `/request` и `/request/:token` работают, E2E на них проходят.
- Проверки: lint, typecheck, 89 unit/integration (+1 todo) на отдельной
  локальной БД; полный Playwright 59/59 в облачной копии. Реальные письма и
  production не затрагивались. Новых зависимостей и миграций нет.
