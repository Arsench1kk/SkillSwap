## Работы и порядок PR

1. **Общая база и разделение монолита.** После PR форматирования D6 выделить
   `prototype-app.tsx` и его CSS по границам D2–D5. Сохранить нынешнее поведение,
   URL, demo-маркировку, keyboard/mobile navigation. Перенести каждый блок вместе
   с локальными типами/стилями; не оставлять две реализации. Экспортировать
   согласованные точки интеграции. Никаких новых экранов в refactor-PR.
2. **Auth и access matrix.** Довести AUTH-1–4: валидация, loading/error, verification,
   resend/reset, истёкшие ссылки, выход и повторный вход. Better Auth остаётся
   владельцем credentials/sessions. Проверить выбранную роль и переключение;
   activeRole пользователя не даёт права оператора. Guard должен проверять
   серверные права; выдачу operator-доступа определить с D5 по R06.
3. **Account ↔ participant.** Выделить повторно используемую серверную операцию
   получения/создания participant по роли из текущей learner-реализации, сохранив
   корректность одновременных первых запросов. D3 использует её для mentor,
   D2 — learner. Не объединять два role-specific ID и не копировать auth email
   в события/контакты. Определить обработку withdrawn по R05/R08.
4. **Контракты модулей.** Вместе с владельцами описать и зафиксировать Zod/TS
   контракты доступа, публичного DTO, ошибок, транзакций и действий первой
   вертикали. D4 должен принимать уже открытую транзакцию подтверждения. Не
   добавлять поля публичного профиля до R01, события до R10.
5. **Целостность и события.** Поддержать атомарные domain-команды: запись состояния,
   state transition и `recordEvent` вместе, единый порядок locks. Проверить
   participant ownership, actor, `data_origin`, template_version, missing_reason,
   append-only ограничения. Согласовать расхождение experiment/UI locale с D6.
   Нельзя менять enum и CHECK только ради прохождения теста без решения.
6. **Миграции и общие утилиты.** D1 — единственный автор schema/auth-schema,
   migrations и Drizzle metadata. Обработать заявки D2–D5 по R01–R10, включая
   A04 session-scoped links и A06 контакт. Проверять чистую установку и upgrade
   существующих данных; старые миграции не переписывать. Поддержать общую
   валидацию дат/контакта и rate-limit scopes без дублирования в фичах.
7. **Сборка кабинета.** Подключать готовые learner/mentor/profile/session модули
   в оболочку небольшими PR, различать auth pending, signed-out и ошибку сессии.
   Ошибка auth не должна незаметно превращать рабочий кабинет в demo. Account
   settings сохраняют только утверждённые настройки; язык подключается из D6,
   профиль/видимость — из D3. Никакой фиктивной persistence через toast/useState.
8. **Совместимость и handoff.** Проверить две роли одного аккаунта, старые приватные
   ссылки, rollback границы миграций, отрицательные auth/access сценарии. Передать
   D6 настройки auth/email, требуемые env и runbook доступа; секреты не включать.

## Приёмка

- Настоящие два аккаунта, обе роли, verification/reset/reload/logout проверены;
  отдельный пользователь не читает/меняет чужие данные, ученик/ментор не оператор.
- Одновременное создание mapping не оставляет дубликатов или лишних participants.
- Миграции применяются на пустую и предыдущую версию; seed только synthetic.
- При ошибке `recordEvent` состояние операции откатывается; actor/identity клиента
  не могут подменить серверный контекст.
- 360 px + клавиатура для AUTH-1–4 и shell, все состояния из UX; новые auth E2E
  в `e2e/account/**`, общие старые specs меняет D6.
- Проверки и требования PLAN пройдены. Каждый PR один concern; общий пакет
  не объединять как одну большую перепись приложения. Новые зависимости перечислить
  с версией/лицензией либо указать «нет».
