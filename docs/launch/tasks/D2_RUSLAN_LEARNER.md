# D2 — Руслан — путь ученика, заявки и поиск

**Ответственный: Руслан.** Код направления: `D2`.

Результат: ученик находит реального наставника по согласованным правилам,
отправляет заявку, отслеживает её, подтверждает/отклоняет время и видит дальнейший
шаг. Подбор и окончательное решение остаются за оператором.

Прочитать обязательные документы в порядке AGENTS, затем [план](../PLAN.md),
[аудит](../AUDIT_2026-11-04.md) и [решения](../DECISIONS.md). Не создавать
поля/экраны/копию вне UX. L1–L3 уже специфицированы; discovery и действие
из публичного профиля требуют R01/R02 и новых утверждённых screen ID/состояний.

## Работы и порядок PR

1. **Матрица пути и экраны.** После G0 принять извлечённые learner/discovery блоки.
   Проверить E0, L1, L2, L3 и account-эквиваленты, составить список состояний.
   Сохранить старый `/request` и `/request/:token`; не заставлять private-link
   пользователя входить. Новый account-путь не должен зависеть от demo-массивов.
2. **Реальная заявка.** Довести общую submit-логику и account GET/POST: серверная
   Zod-проверка, eligibility, 2–3 окна, даты Казахстана, give-back, согласие,
   контакт отдельно от событий, rate limiting. Сохранение черновика, reload,
   сетевые ошибки/повтор, pending и отсутствие потери текста. Устранить A06 с
   D1 после выбора модели контакта; повторные заявки с другим контактом проверить.
3. **Список и детали.** Подключить настоящие заявки и разрешённые действия;
   loading/empty/error/retry/withdrawn/expired/terminal состояния — по UX.
   Использовать enum статусов БД, не вымышленные `slot_proposed`/`confirmed` как
   статусы learner_request. Различать статус заявки, brief и match. После reload
   тот же результат; смена аккаунта/роли не показывает старые данные.
4. **Подтверждение и восстановление.** Довести cancel/update/confirm/decline,
   уход наставника и отмену встречи согласно R07. Проверять свежие состояния
   внутри транзакции; согласовать порядок locks с D3/D4. Подтверждение вызывает
   сервис D4 в той же транзакции; гарантировать одну встречу и правильное событие.
   Не создавать session напрямую и не вызывать HTTP после commit.
5. **Поиск реальных наставников.** После R01–R03 реализовать read-сервис и UI
   согласованных поиска/фильтров/порядка/страниц результатов. D3 предоставляет
   public projection и правило публикации: скрытые/неподтверждённые/снятые
   профили не появляются через запрос, count или API. Не отдавать contact/proof
   reference/email из внутренних таблиц. Пустая выдача — реальное состояние.
6. **Профиль → заявка.** Отобразить утверждённый публичный компонент D3 и связать
   его primary action с L1 по R02. Не считать выбор человеком автоматическим
   назначением наставника. Поведение устаревшего/скрытого профиля и отсутствие
   доступности согласовать в UX; не добавлять прямой чат, цены или рейтинги.
7. **События и доступ.** Для каждого действия применить существующее утверждённое
   событие, server participant/data_origin и template version где требуется.
   Новые действия поиска/профиля сначала согласовать в R10. Тестировать ownership
   настоящей сессией: без входа, чужой request ID, неверная роль, отозванное
   согласие по политике. Не выдавать приватный token в публичной выдаче.
8. **Приёмка и связка.** Пройти с D5/D3/D4 путь от пустого аккаунта до встречи,
   включая отказ, повторный подбор, network error и повторный submit. Передать
   D6 cross-role сценарий без ручной вставки match/session. Для E0 убрать
   устаревшие объяснения только по согласованному тексту; редизайн не цель.

## Зависимости и контракты

От D1: auth/participant/transactions, contract/types и A06 миграция. От D3:
утверждённый profile DTO и единый visibility predicate. От D4: транзакционный
ensure-session контракт и API чтения встреч. D5 получает eligibility/match
операции learner-модуля, а не право менять их обходным SQL. D6 заранее добавляет
ключи и предоставляет i18n server/client resolver.

Независимо от решений по профилям можно исправлять L1–L3, доступ, черновики,
статусы и писать регрессионные тесты существующих сценариев.

## Приёмка

- Регрессии A06; подтверждение/отмена/отказ и конкуренция с withdraw; повторные
  запросы не создают два принятия/две встречи; состояние и события атомарны.
- Поиск выдаёт только допустимые public fields; privacy проверена прямым API,
  а не только отсутствием карточки на экране.
- Черновик переживает error/reload; новый пользователь получает честные пустые
  списки; кабинет после повторного входа показывает сохранённое.
- По одному 360 px smoke на утверждённый экран, keyboard и все UX-состояния;
  Impeccable critique/detector и стандартные проверки PLAN.
- Автор фичи пишет свои unit/integration/E2E; D6 собирает общий happy path.
  Невыбранные продуктовые решения перечислить явно, не заменять demo-заглушкой.
