# D3 — Амир — наставник, профили, видимость и приглашения

**Ответственный: Амир.** Код направления: `D3`.

Результат: наставник связан с аккаунтом, сохраняет настоящий профиль и навыки,
проходит ручную проверку и отвечает на приглашения. Публичная выдача получает
только согласованные данные. Профиль не является доказательством сертификации.

Прочитать документы по AGENTS, затем [план](../PLAN.md),
[аудит](../AUDIT_2026-11-04.md) и [решения](../DECISIONS.md).

видимость и модерация требуют R01/R03/R04: сначала утверждённые поля, screen ID,
состояния и event mapping, затем реализация.

## Работы и порядок PR

1. **Подготовить спецификацию профилей.** Собрать вопросы R01/R03/R04 и имеющиеся
   противоречия документов. Предложить варианты видимости/проверки, не объявляя
   demo-поля утверждёнными. Отдельно описать собственное редактирование, публичную
   карточку и приватную компетенцию для пары. Оценки/отзывы публичными не делать.
2. **Account mentor onboarding.** Использовать role-specific mapping D1. Сейчас
   публичный join создаёт нового participant и не связывает его с аккаунтом;
   исправить account-путь без поломки существующей M1 формы. Proof остаётся
   reference, без новой системы загрузок. Контакт/доказательства не идут в events.
   Повторное открытие/отправка не плодят разные профили того же аккаунта.
3. **Настоящее редактирование.** По утверждённым полям реализовать серверное чтение,
   validation/save/cancel и reload-проверку; разделить сохранённое и черновик.
   Ошибка сохранения сохраняет ввод. Удалить зависимость рабочего профиля от
   demo `useState`. Чужой аккаунт и переключение роли не дают редактировать профиль.
4. **Публикация и privacy.** Реализовать согласованный lifecycle видимости,
   правила показов и public projection как единый сервис. Именно его получает
   D2; отдельный detail endpoint соблюдает те же ограничения, что поиск.
   Скрытие/модерация действует на сервере сразу по утверждённой политике.
   Contact, email и raw proof references не становятся публичными случайно.
5. **Проверка навыков и moderation-сервис.** Развить `setSkillVerification` по
   R03/R04: только оператор, сохраняется происхождение решения, невозможна
   самостоятельная верификация. Команды проверки и снятия публикации предоставить
   D5; операторский UI/очередь не писать параллельно с ним. Требуемые события
   сначала утверждаются в R10, а миграции выполняет D1.
6. **Настоящие приглашения.** Кабинет наставника получает только его briefs,
   детали и допустимые действия. Переиспользовать логику M2, а не вторую
   независимую реализацию состояний. Предложение времени, изменение до принятия,
   decline с закрытым reason code, withdrawal и read-only после подтверждения.
   Предложение не отменяет право оператора на ручное решение.
7. **Исправить M2.** A07: answer-by не должен сам подменять срок доступа уже
   подтверждённого brief. A08: viewed и `mentor_viewed` пишутся атомарно.
   При нескольких приглашениях/попытках одному наставнику выбрать точную связь
   brief↔match по согласованному контракту, не произвольный `.limit(1)`.
   Учесть concurrent propose/confirm/withdraw по locks-контракту D1/D2/D4.
8. **Интеграция и качество.** Передать D2 public DTO, D5 verification/moderation
   команды, D4 данные выбранной пары. Подключить i18n D6 и 360 px состояния.
   Не переводить все серверные тексты руками в нескольких местах; использовать
   общий resolver. Проверить privacy после изменения настроек и повторного входа.

## Приёмка

- Реальный mentor-аккаунт отправляет анкету и видит тот же профиль после reload;
  одна учётная запись корректно работает как learner и mentor с разными IDs.
- Версия публичных данных проходит матрицу R01; hidden/moderated/withdrawn
  профили недоступны и по прямому API в пределах согласованной политики.
- Ученик/ментор не может выдать verified; proof и contact остаются приватными.
- M2 регрессии: confirmed после answer-by при действующем link; откат viewed
  при падении event; несколько повторных briefs; pending/error/expired/declined/
  withdrawn/confirmed и одновременные действия.
- Все значимые действия используют утверждённые события и server context.
- Стандартная приёмка PLAN: собственные тесты, 360 px + keyboard, Impeccable,
  strings/tokens, работа без заглушек; каждый PR один concern.
