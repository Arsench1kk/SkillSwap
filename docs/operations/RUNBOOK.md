# SkillSwap: эксплуатационная инструкция (runbook)

Владелец документа: D6 (Андрей). Решения о хостинге, доступах, сроках и
ответственных утверждает команда. Здесь **нет значений секретов**: только
имена переменных и порядок действий. Статус каждого пункта — в
[release checklist](../launch/RELEASE_CHECKLIST.md).

Текущее размещение (по [WEBSITE_TEST_WORKFLOW_RU](../WEBSITE_TEST_WORKFLOW_RU.md)):
приложение на Vercel, PostgreSQL на Neon. Если команда сменит платформу,
поменяются команды, но порядок шагов останется тем же.

## 1. Окружения

| Окружение  | Приложение                       | База данных                                | `SKILLSWAP_DATA_ORIGIN` | Почта                                   |
| ---------- | -------------------------------- | ------------------------------------------ | ----------------------- | --------------------------------------- |
| local      | `npm run dev`                    | Docker `localhost:5433/skillswap`          | `rehearsal`             | выкл. или dev-обход (только localhost)  |
| test / CI  | Playwright dev-сервер, порт 3100 | `*_test` на localhost, пересоздаётся       | `rehearsal`             | dev-обход; реальных писем нет           |
| staging    | Vercel Preview (отдельный URL)   | **отдельная** Neon-ветка/БД `staging`      | `rehearsal`             | Resend, тестовый отправитель/получатели |
| production | Vercel Production                | Neon `main`, доступ только у ответственных | решение R10             | Resend, проверенный домен отправителя   |

Правила:

- Staging и production никогда не используют одну БД. Строку подключения
  production не держать в `.env.local` разработчика: `vercel env pull` для
  production не выполнять на ноутбуке, где запускаются тесты.
- Тесты физически не могут обратиться к Neon: guard `testing/database-target.ts`
  отказывается работать с нелокальным хостом и БД без сегмента `test`.
- `AUTH_DEV_SKIP_EMAIL_VERIFICATION` не задавать в staging/production (код и так
  игнорирует его вне development + localhost).

`ci.yml` содержит только фиктивный `BETTER_AUTH_SECRET` для сборки; это не
секрет. Реальные значения не попадают в Git, логи и тикеты. Ротация секрета:
сгенерировать новый (`openssl rand -base64 32`), заменить в Vercel env,
передеплоить; смена `BETTER_AUTH_SECRET` завершает все активные сессии.

## 3. Auth и почта

- `BETTER_AUTH_URL` и `NEXT_PUBLIC_APP_URL` равны публичному URL окружения
  (staging — свой). Они же — единственный trusted origin (`src/lib/auth.ts`).
- Отправитель `AUTH_EMAIL_FROM` должен быть на домене, проверенном в Resend
  (SPF/DKIM). Для staging — отдельный ключ Resend.
- **Проверка доставки** (только staging, только на почту участников команды):
  зарегистрировать тестовый аккаунт → письмо подтверждения пришло, ссылка ведёт
  на staging-URL → запросить сброс пароля → письмо пришло, ссылка одноразовая.
  HTTP 200 от `requestPasswordReset` **не доказывает** отправку (см. D1-H006):
  смотреть Resend dashboard и серверный лог `Transactional email` ошибок.
- Язык писем: `src/i18n/auth-email.ts` (D6-H003); подключение в `auth.ts` — D1.

## 4. Порядок выпуска и миграций

Миграции идут только вперёд (drizzle journal). Порядок для staging, затем production:

1. CI на коммите зелёный (static, тесты, clean + upgrade миграции, build, E2E).
2. **Резервная копия** production (раздел 5) — перед любой миграцией.
3. Применить миграции явно к целевой БД, отдельным шагом до деплоя:
   `DATABASE_URL=<из секрет-хранилища> npm run db:migrate` (из `apps/web`).
   Не встраивать миграцию в `next build`.
4. Задеплоить приложение (promote preview → production в Vercel).
5. Smoke: `/`, `/login`, `/privacy`, одна приватная ссылка staging, вход
   тестовым аккаунтом; проверить серверные логи на ошибки.
6. Записать в checklist: SHA, время, кто выполнял, результат smoke.

Новая миграция должна быть совместима с предыдущей версией приложения
(расширение схемы, затем код, затем удаление старого — разными выпусками),
чтобы откат приложения не требовал отката схемы.

## 5. Резервное копирование и восстановление

- Neon: включённая point-in-time recovery и ветки — основной механизм. Срок
  хранения PITR зависит от тарифа; утверждает команда.
- Логическая копия перед каждой миграцией production:

  ```sh
  pg_dump "$DATABASE_URL" -Fc --no-owner --no-privileges -f skillswap-YYYYMMDD-HHMM.dump
  ```

  Файл содержит персональные данные: хранить только в согласованном
  зашифрованном месте с ограниченным доступом, не в Git и не в чатах; срок
  хранения — решение R05.

- Восстановление в **новую** БД (никогда поверх рабочей):

  ```sh
  createdb skillswap_restore
  pg_restore -d skillswap_restore --no-owner --no-privileges --exit-on-error skillswap-....dump
  ```

  Затем сверить число строк ключевых таблиц и `drizzle.__drizzle_migrations`,
  переключить `DATABASE_URL` приложения и передеплоить.

- Проверено 16.11.2026 локально (PostgreSQL 17.10): dump/restore тестовой БД,
  совпали счётчики `participants`, `events`, `sessions`, `user`, миграций; триггер
  append-only на `events` после восстановления работает. На staging/Neon
  восстановление ещё не проверялось — это пункт checklist.

## 6. Откат

| Ситуация                                 | Действие                                                                                                                                    |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Ошибка в коде, схема не менялась         | Vercel: «Instant rollback» на предыдущий production-деплой                                                                                  |
| Ошибка в коде после совместимой миграции | Откат приложения; схема остаётся (миграции совместимы назад)                                                                                |
| Миграция повредила данные                | Остановить запись (maintenance), восстановить из копии шага 4.2 в новую БД / Neon PITR-ветку, переключить `DATABASE_URL`, разобрать причину |
| Утечка секрета                           | Ротация (раздел 2), проверить логи доступа, сообщить ответственному за safety                                                               |

Откат миграции вручную SQL-ом не выполнять: исправление — новой миграцией D1.

## 7. Фоновые задачи

| Задача                     | Entry point                  | Владелец | Cadence         | Статус                 |
| -------------------------- | ---------------------------- | -------- | --------------- | ---------------------- |
| Истечение окна отзыва (L5) | `npm run db:expire-feedback` | D4       | решение команды | вручную через workflow |
| no-reply / follow-up       | нет в коде                   | D4/D5    | решение R11     | не реализовано         |

`.github/workflows/ops-jobs.yml` запускает задачу **только вручную**
(workflow_dispatch) в выбранном GitHub Environment (`staging`/`production`) с
секретом `DATABASE_URL` этого окружения. Для `production` в настройках
репозитория включить required reviewers. Расписание (cron) добавляется после
согласования cadence и доступов; задача идемпотентна, повторный запуск безопасен.

## 8. Мониторинг и логи

- Источник: логи Vercel функций и Neon метрики; отдельная analytics-платформа
  не добавляется (AGENTS).
- Следить: 5xx на `/api/**`, ошибки `Transactional email`, отказы `rate_limited`,
  падения ops-jobs workflow (уведомление GitHub ответственному).
- В логах нельзя: контакты, имена, email, сырые токены приватных ссылок,
  полный ответ провайдера почты. Код уже логирует без них (D1-H006/H007);
  новые логи проверять на ревью по этому правилу.
- Кто реагирует и в какой срок — решение R05 (safety owner) и R06.
